# nf-fairscape changelog

## Unreleased

- **The port is now checked against fairscape-cli automatically, on every push** (`make parity-test`, `src/test/groovy/nextflow/prov/parity`). The plugin re-implements seven things the CLI does — inverse entailment, the inputs/outputs entailment, the evidence graph and its viewer, the LinkML/D4D export, the AI-Ready score, the datasheet, and tabular schema inference — and until now the only check was `tools/parity.sh`, a script someone had to remember to run against a crate they happened to have. There are now five specs over three committed crates, and each hands the *same* directory to both implementations (the CLI performs the preparation steps) so a failure means the two diverged rather than that they were given different inputs. `provenance-graph.json`, `provenance-graph.html`, `ro-crate-linkml.yaml` and `ai_ready_score.json` are asserted **byte-identical**; `ro-crate-datasheet.html` after two documented normalizations; the inferred schema minus the CLI's uuid `@id` and its version stamp. The fixtures are real crates frozen by `tools/make-parity-fixtures.sh` with every derived artifact turned off, since deriving them is the thing under test — `letters-chain` (a plain publish chain), `nf-test` (expanded directories, checksums, an inferred schema) and `fanout` (the synthetic shape that reaches `GraphCondenser`). `tools/parity.sh` stays, unchanged, as the interactive form: point it at any crate directory, including real pipeline output, and it prints the diffs.
- CI installs the **latest fairscape-cli from PyPI**, deliberately unpinned: the CLI is the ground truth, so a release that changes any of those outputs should turn the check red rather than be papered over by a version pin. The specs skip when the CLI is not importable — `make test` has to stay runnable without a Python environment — so the CI job sets `FAIRSCAPE_PARITY_REQUIRED=1`, which makes a missing CLI a failure instead of a suite that passes having compared nothing.
- Split CI into three workflows, one concern each: **nf-fairscape CI** (compile and unit tests, no Python, no Nextflow), **Parity vs fairscape-cli** (the suite above; needs no Nextflow, because the fixtures are committed crates), and **RO-Crate 1.2 validation** (installs the plugin, runs `nf-fairscape-test` *and* `examples/letters-chain` under Nextflow, and validates each published crate). The last one is not a parity check: it asks only whether a real pipeline run produces a crate that validates. All three now run on every push, not just `main`.
- Fixed: **6 of the 9 `CrateArtifactsTest` tests failed on a fresh checkout**, so the existing CI job's unit-test step was passing only on machines that happened to have run the example. The test read its crate from `examples/letters-chain/results`, which `.gitignore` excludes along with every other crate — as it should, since example output does not belong in git. It now reads the committed parity fixture. The same rules would have swallowed the new fixtures, so `src/test/resources/parity/**` is explicitly re-included.
- `validate_crate.py` also checks the two declarations that make a crate an RO-Crate 1.2 rather than generic JSON-LD that happens to parse: the descriptor's `conformsTo` and that its `about` points at the root entity. `ROCrateV1_2.model_validate` accepts any graph its member models accept, and says nothing about which profile the crate claims.
- Confirmed and documented a limit on the datasheet parity claim: `ro-crate-datasheet.html` **cannot** be byte-identical, because the CLI's own output is not stable. `fairscape_models/conversion/mapping/subcrate_utils.py` builds the composition patterns with `list(set(...))`, so running `fairscape build datasheet` on one unchanged crate under different `PYTHONHASHSEED` values produces two different files. The suite compares that list as the set it is. `ro-crate-linkml.yaml` and `ai_ready_score.json` were checked the same way and are deterministic, so their byte-identical claims stand as stated.

- **The crate carries the workflow that produced it** (`includeWorkflow`, default on). The workflow script and every config file the run used are copied into `<crateDir>/workflow/`, and every Software entity whose defining file was copied points its `contentUrl` at that copy — the workflow itself, and each process declared in the same file, which in a single-file pipeline is all of them. Before this, a crate could not reliably say what was run: a local pipeline normalized to `file:///home/you/pipeline/main.nf`, which resolves on exactly one machine, and a registry pipeline pointed into `~/.nextflow/assets/nf-core/<name>` — a cache shared by every run of it and overwritten on update. Neither survives zipping the crate and handing it to someone. Copying was chosen over the alternative of writing the crate into the directory that holds `main.nf`: that works for a local pipeline but not a registry one, where the script sits in a shared cache no per-run output belongs in, and it would put run artifacts in your source tree. `codeRepository` still records the origin and nf-core module entities still carry commit-pinned URLs — modules are not copied, and a pinned URL beats a copy anyway — so nothing is lost. The configs are described as Datasets (`isPartOf` the workflow Software) rather than left as undeclared bytes, and since nothing generated them they entail as crate **inputs**, which is what a file that parameterizes a run is.
- **A Dataset outside the crate no longer claims a path inside it.** A relative `contentUrl` is a promise that the file is at that path under the crate root — [RO-Crate resolves it there](https://www.researchobject.org/ro-crate/specification/1.2/data-entities.html), and 1.2 has no way to spell one that escapes. Work-directory intermediates are not under the crate root, so the path they got resolved to nothing: 44 of 130 entities on differentialabundance pointed at `work/…` from a crate rooted at `results/`. Those now carry [`localPath`](https://w3id.org/ro/terms#localPath) instead — RO-Crate's term for *the file was here when this ran*, which is the honest reading of a directory Nextflow may already have deleted. Files that really are in the crate keep `contentUrl`, and so do pipeline assets and remote inputs, which normalize to absolute URIs (a pinned GitHub URL, `s3://…`) and resolve from anywhere. The entity keeps its `name`, `md5`, `contentSize` and every provenance edge either way, so the derivation chain through unpublished intermediates is unchanged — only the false locator is gone. `localPath` is declared in the crate `@context` as a bare term, spelled as [RO-Crate 1.2's own context](https://w3id.org/ro/crate/1.2/context) spells it, so a consumer reading with either one gets the same IRI.
- **Documented precondition: publish with `mode: 'copy'` if the crate is going anywhere.** A crate-relative `contentUrl` means the path is right; it does not mean the bytes travel with the crate, and the plugin cannot tell the difference. Nextflow's default publish mode is `symlink`, and a symlinked published file sits under the crate directory like any other, so it gets a relative `contentUrl` while its bytes stay in `work/` — zip that crate and you ship dangling links. nf-core pipelines set `publish_dir_mode = 'copy'` and are unaffected; a hand-written pipeline that never sets `mode` is not. See [docs/FAIRSCAPE.md](docs/FAIRSCAPE.md#precondition-publish-with-mode-copy-if-you-want-a-portable-crate).
- New [`examples/nf-core/verify-against-run.py`](examples/nf-core/verify-against-run.py): checks the evidence graph against the run it describes, rather than against itself. `validate_crate.py` answers *is this a valid EVI RO-Crate* and `check-crate.py` answers *does it have the properties a real nf-core crate needs* — a crate that describes a completely different workflow, perfectly, passes both. This rebuilds the run's provenance from artifacts the plugin does not write and cannot influence (the execution trace, each task's `.command.sh`, the `nxf_stage()` block naming exactly what it consumed, the files left in its work directory) and diffs the two, joining on `Computation.identifier` == the task hash and `Dataset.md5` == the bytes. An edge the crate asserts that the run does not support fails; an edge the run has that the crate omits is counted, since unpublished intermediates are legitimately out of scope. It found the `contentUrl` defect above, and one still open (below).
- Fixed: `run.sh` could not re-run a pipeline. It runs from `<pipeline>/`, where Nextflow auto-loads `nextflow.config` — which after any successful run is the *pipeline's own* config, copied there so the graph can be read against it. It includes `conf/base.config`, which is not copied, so every `-resume` died on a missing config file despite the README documenting `-resume`. The reference copies are now cleared before the run and rewritten after it.

- Hardened against real nf-core pipelines. Five released pipelines were run end to end with every option on — demo 1.2.0, phyloplace 2.0.1, pairgenomealign 3.0.3, differentialabundance 2.0.0, seqinspector 1.1.0 — plus a check that the plugin behaves identically on Nextflow 26.04.6, which the newer two require. Everything below came out of those runs.
- Three new examples, so those runs are repeatable rather than described. [examples/nf-core](examples/nf-core) is the regression set itself: `./run.sh` fetches each released pipeline from GitHub, runs it unmodified with nothing but a `-c` config that switches the plugin on, and then checks the crate — `validate_crate.py` for validity, and a new `check-crate.py` for the six properties that only go wrong once a real pipeline is on the other end (acyclic graph, evidence graph actually written, author not the local user, tool versions read, no schema headed by a comment, ARK slugs distinct). Each pipeline gets its own `results/` to inspect. [examples/cycle-repro](examples/cycle-repro) is the crash reduced to two processes and no containers; [examples/edge-cases](examples/edge-cases) is the publishing and tabular oddities a crate has to survive, including the one that still produces junk (a `.csv` holding gzip bytes) so the gap stays visible.
- **The provenance graph is now guaranteed acyclic, and differentialabundance stops losing its evidence graph.** nf-core 3.4+ collects tool versions through `channel.topic('versions').collectFile(...)`, which means *Nextflow* writes `collated_versions.yml`: no task produced it, so it counted as an input the run used, and it is also published, so the run generated it. Inverse-linking closed the loop and `EvidenceGraphBuilder` recursed until the stack died — the crate was still written and valid, but `provenance-graph.json`/`.html` were missing and the root had no `localEvidenceGraph`. Fixed where the cycle was created rather than where it was tripped over: a Computation's `usedDataset` no longer contains anything from its own `generated`, since nothing can be its own ancestor. The task that actually read the file keeps its own edge, so no evidence is lost. The graph walk also carries an in-flight guard now, so a crate some other tool made cyclic is walked as far as it can be instead of aborting the whole artifact.
- **`author` no longer defaults to whoever ran the pipeline.** nf-core replaced `manifest.author` with `manifest.contributors`, so every modern pipeline was falling through to the local Unix username — the crates said `oj` where the manifest names Christopher Hakkaart, Charles Plessy, or seven credited authors. Contributors whose `contribution` includes `author` are used, otherwise everyone is named.
- **Process Software entities report the version of the tool that ran, not the pipeline's** (`toolVersions`, default on). A FastQC entity claiming version `1.2.0` because that is the pipeline's release is worse than no version at all. The real one is read from whichever place the module put it: the `versions.yml` a task writes, or the run-wide `pipeline_info/*_software_mqc_versions.yml` that newer modules populate through a `topic` channel with `eval` instead of writing any file of their own. FastQC 0.12.1, seqtk 1.4-r122, LAST 1652, `bwamem2 2.2.1, samtools 1.22.1`. MultiQC keeps the manifest fallback by construction — the collated file is built before MultiQC runs, because MultiQC is what consumes it.
- **The samplesheet is in the crate** (`paramInputs`, default on). `params.input` is parsed in the workflow body by nf-schema and never staged into a task, so the run's primary input reached the crate as nothing but a string in `parameter`: four of the five pipelines had no CSV Dataset at all, and `schemas = true` had nothing to describe. File-shaped parameter values are now registered as inputs of the run, which also means the samplesheet gets a schema (`sample,fastq_1,fastq_2`).
- **A MultiQC table is described by its real header.** `*_mqc.tsv` files open with a `# id: '...'` preamble, and inference took the first comment line as the header — emitting a one-column schema whose column was literally named `# id: 'contigs_length_statistics'`, marked required. New `schemaCommentChar` (default `#`) skips the preamble, while a BED-style `#chrom<TAB>start<TAB>end` line still counts as a header because it splits into as many fields as its data. Set it to `''` for the CLI's behaviour.
- **Process ARKs are readable again.** nf-core process names are fully qualified, so `NFCORE_PAIRGENOMEALIGN:PAIRGENOMEALIGN:PAIRALIGN_M2O:ALIGNMENT_LASTDB` ran past the 40-character slug cap and six of twelve entities in one run shared the id stem `software-nfcore-pairgenomealign-pairgenomealign-p`. The slug now comes from the bare process name (`software-alignment-lastdb-…`). Only the readable half changed: the hash still covers the qualified name, so two aliases of one module stay distinct and `-resume` reproduces the same ARK.
- **One published MultiQC folder no longer reports a thousand crate outputs.** With `expandDirectories` on, every file inside a published directory looked terminal to the outputs entailment, so seqinspector's root listed 1020 outputs and the evidence graph started a walk from each one — 1187 nodes and a 1 MB viewer. Files that are `isPartOf` a directory Dataset are now left to the directory that stands for them: 35 outputs, 202 nodes, 411 KB.
- Process Software descriptions are valid source again. The body of an nf-core module opens with a Groovy prologue before its triple-quoted command, so stripping only the leading and trailing delimiters left the opening `"""` in the text and deleted its partner.

- New [docs/CONFIGURATION.md](docs/CONFIGURATION.md): every option with type, default, cost and effect; both metadata hooks (`fairscape.metadata`, `ext fairscape`) with the full key catalogue taken from the `ROCrateMetadataElem` model that validates the root; each AI-Ready sub-criterion mapped to the setting that satisfies it; recipes and gotchas. README is now a grouped index onto it — its old table was missing `containerProvenance` and `containerEngineCommand` entirely. FAIRSCAPE.md keeps the crate semantics and links across.
- Newly documented: `patterns` auto-anchors with `**/` but `expandPatterns`/`schemaPatterns` match the full path; `overwrite = false` aborts a re-run rather than skipping the crate; `published = true` only changes the datasheet accession link; colon keys (`rai:dataBiases`) must be quoted in Groovy; an undeclared root key expands against schema.org's `@vocab` to a URI that resolves to nothing, so `additionalProperty` is the place for custom fields.
- Measured, not asserted: the test pipeline scores 17/28 on the AI-Ready rubric with no metadata and 28/28 with the "everything on" recipe, crate still valid under `ROCrateV1_2.model_validate`.

- `containerProvenance = true` describes the container each task ran in. Task Computations have always carried `containerImage`, but that is the image *reference* the `container` directive resolved to — usually a tag, and a tag can be repointed at different bits tomorrow, so two runs a month apart are indistinguishable in the crate. With the option on, each distinct image is resolved once via the container engine (`nextflow/prov/util/ContainerInspector.groovy`) and the crate gains `containerDigest` on the task Computations plus `containerImage`/`containerDigest`/`containerImageId` on the **process Software** entity — the image is that software's built artifact, so it belongs next to the tool it distributes rather than only on each activity. New `containerEngineCommand` option for when the engine binary is not on the PATH under its usual name; Singularity/Apptainer are deliberately not guessed at, since they run image files with no daemon to ask. Off by default (it shells out once per distinct image), and best-effort throughout — a missing engine or a timed-out inspect leaves the crate exactly as it was.
- A digest pins content, not availability, and the code says so rather than overclaiming: under Docker's containerd image store `Id` *is* the manifest digest, so it and the repo digest are the same string both for a pulled image (`cm4ai/cellmaps_ppidownloader:0.2.2` → `sha256:85b359d3…`, matching what Docker Hub serves) and for a locally built one that exists on exactly one machine. The presence of a repo digest is therefore not evidence the image can be pulled from anywhere.
- Verified opt-in: with the option off the crate is unchanged. Proven by reconstructing the pre-change plugin from the same working tree (these edits reverted, everything else kept) and diffing `examples/letters-chain` run for run — identical once ARK hashes, timestamps, the session id and the launch command are normalized, and none of the three new keys appears anywhere. The one difference that does turn up between any two runs is the order of the run-level `generated` list, which flips on roughly 2 runs in 10 **in the unmodified baseline** (publish-event ordering), so it is pre-existing nondeterminism rather than an effect of this change.

- Groovy port of `fairscape augment link-inverses` (`datasheet/InverseLinker.groovy`), run before the inputs/outputs entailment like the CLI's `process_subcrate`. Completes the 18 `owl:inverseOf` pairs EVI declares, carried as a table rather than re-derived with rdflib + SPARQL at runtime. Most visibly it fills `generated` on a Computation for every file that names it in `generatedBy`, so the files found inside a published directory finally appear on the step that produced them (`HIERARCHY.generated` 1 → 24 on the Cell Maps pipeline). New `linkInverses` option, default `true`.
- Groovy port of `fairscape build linkml` (`datasheet/D4dConverter.groovy` + `datasheet/PyYaml.groovy`): the crate root translated into a D4D (Datasheets for Datasets) document at `ro-crate-linkml.yaml`. `PyYaml` reproduces `yaml.dump`'s defaults — sorted keys, block style, 80-column folding, plain/single/double style selection and the `\` continuations of the double-quoted form — so the output diffs clean against the CLI. New `linkml` option, default `true`.
- `tools/parity.sh` grew a stage 0 (link-inverses, compared on the parsed graph since the two sides format JSON differently) and a `ro-crate-linkml.yaml` diff. Both are byte-identical to `fairscape-cli`, as are the augmented graphs on the Cell Maps, letters-chain and nf-fairscape-test crates.

- Groovy port of `fairscape-cli schema infer` for csv/tsv (`nextflow/prov/schema/TabularSchemaInferrer.groovy`), reproducing frictionless's candidate-type detection and fairscape's canonical-type mapping. `schemas = true` attaches an `EVI:Schema` node to every described tabular file via `evi:schema`; `schemaArrayThreshold` collapses a wide embedding table into one spanning-array property. New `schemas`, `schemaPatterns`, `schemaSampleSize`, `schemaArrayThreshold` and `schemaMaxFiles` options. Verified column-for-column against the CLI on 27 real pipeline outputs.
- `expandDirectories = true` describes the files inside a published directory as Datasets of their own (`isPartOf` the directory, `generatedBy` the task that produced it), so a process whose output is a directory no longer contributes one opaque, sizeless Dataset. New `expandPatterns` and `expandMaxFiles` options.
- `checksums = true` records an `md5` on every Dataset that resolves to a readable local file — what the AI-Ready "verifiable" criterion looks for.
- `contentSizes = true` measures directories as well as files: a recursive `contentSize` per directory Dataset and the crate directory's total payload on the root, so the AI-Ready "statistics" criterion stops reading only the input files.
- All four of the above are **off by default and the emitted crate is unchanged without them** — verified by re-running `examples/letters-chain` with its stock config and diffing against the pre-change crate: `ai_ready_score.json` identical, `ro-crate-metadata.json` identical once run-to-run ARK hashes, timestamps and the session id are normalized. They each cost extra I/O (a directory walk, a full read per file, a parse per table), which is the reason they are opt-in rather than on.
- One unconditional change: a Dataset that is a directory is now described as `Directory 'x' …` instead of `File 'x' …`.

- Groovy port of `fairscape build datasheet` and `fairscape build evidence-graph`, run automatically once the crate is written: `provenance-graph.json`, a self-contained `provenance-graph.html` viewer, `ro-crate-datasheet.html` and `ai_ready_score.json`. New `datasheet`, `evidenceGraph` and `published` config options (the first two default to `true`). See [docs/DATASHEET.md](docs/DATASHEET.md).
- The crate root now carries `EVI:inputs`/`EVI:outputs` (ported from the CLI's `find_outputs` entailment) plus `localEvidenceGraph`, so the evidence graph can be rooted at the crate and reproduced by the Python CLI.
- Evidence-graph condensation collapses more than five sibling datasets with an identical provenance signature into one `EVI:DatasetGroup`, so scattered workflows stay readable.
- `tools/parity.sh` diffs both artifacts against `fairscape-cli`; the graph JSON/HTML and the AI-Ready score are byte-identical.

- One `EVI:Software` node per process (`isPartOf` the workflow-script Software, `contentUrl` = defining script/module file). Task Computations now reference their own process via `usedSoftware`; only the run-level Computation references the workflow script and the Nextflow engine.
- Process Software `description` is the process body source as written in the workflow (the unresolved template; the resolved command remains on each Computation).

## 0.1.0

Initial release, forked from [nf-prov](https://github.com/nextflow-io/nf-prov) v1.7.0.

- New `FairscapeRenderer` emitting a FAIRSCAPE EVI RO-Crate (`ro-crate-metadata.json`) conforming to RO-Crate 1.2, the FAIRSCAPE profile 0.1, and the EVI ontology.
- New flat `fairscape` config scope replacing `prov.formats.*`; every required EVI field has a fallback so a zero-config run produces a valid crate.
- Deterministic ARK identifier minting (`ark:{naan}/{prefix}-{slug}-{sha1[0:7]}`), stable across `-resume`.
- Removed the BCO, DAG, GEXF, and WRROC renderers.
- Successful native (`exec:`) tasks are recorded as Computations (upstream nf-prov drops them on fresh runs).
- Python validation oracle (`nf-fairscape-test/validate_crate.py`) against the `fairscape_models` schema.
